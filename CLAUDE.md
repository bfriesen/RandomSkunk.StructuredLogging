# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

RandomSkunk.StructuredLogging: modern structured logging extensions for .NET that separate human-readable messages from machine-readable attributes. It replaces `Microsoft.Extensions.Logging.Abstractions`'s `LogDebug`/`LogInformation`/etc. extension methods, which force every structured property into the message template. This library lets a message be formatted however the caller wants while structured properties are attached separately and explicitly.

## Environment

This is a WSL environment with no Linux .NET SDK installed. Use the Windows SDK via `cmd.exe`, e.g.:

```bash
cmd.exe /c "dotnet build"
cmd.exe /c "dotnet test"
```

The SDK version is pinned in `global.json` (currently 10.0.301).

### The public API shape

`StructuredLoggerExtensions` (generated) exposes, for each of `Trace`/`Debug`/`Information`/`Warning`/`Error`/`Critical`, plus a level-as-argument `Write`:

- 4 `EventId`/`Exception` combinations (both, `EventId` only, `Exception` only, neither)
- × 7 structured-property shapes: no properties, generic arity 1–6 via `(string Name, T1 Value) logProperty1, ...` (avoids boxing for small property counts). There's no arbitrary-count `params` overload — a caller with more than 6 statically-known properties builds a collection instead.
- × 2 collection variants: each of the 7 shapes above also has a sibling overload with a leading `IReadOnlyCollection<KeyValuePair<string, object?>> logProperties` parameter immediately after `this ILogger logger` (accepts a previously constructed `Dictionary<string, object?>` or `List<KeyValuePair<string, object?>>`), letting a caller combine that collection with statically-known properties in the same call.
- × 2 message-parameter shapes: every combination above is generated twice, once with the message parameter typed as the level's `[InterpolatedStringHandler]` struct and once typed as plain `string`.

= 784 methods total.

The interpolated-handler message parameter is a custom `[InterpolatedStringHandler]` struct (one per level, plus a level-generic one for `Write`). Its constructor checks `logger.IsEnabled(level)` and, if disabled, sets `handlerIsValid = false` — the C# compiler then skips evaluating the interpolation holes entirely (they're never appended, never formatted), so `logger.Debug($"... {ExpensiveCall()}")` doesn't call `ExpensiveCall()` when the Debug level is disabled. There is no implicit conversion from `string` to the handler type; instead, a separate `string message` overload exists for every combination, so a plain string argument (constant or not) binds directly to it — no handler construction, no formatting work, just an explicit `IsEnabled` check before logging. Per the C# spec's interpolated-string betterness rule, an interpolated string literal (`$"..."`) still prefers the handler overload over the `string` overload when both are applicable, so `logger.Debug($"literal")` gets the handler's tag-capturing behavior while `logger.Debug(someStringVariable)` gets the plain overload. The handler-typed `message` parameter is declared `ref` (e.g. `ref DebugInterpolatedStringHandler message`) to avoid copying the ref struct (which embeds a `DefaultInterpolatedStringHandler`, itself a ref struct) into the callee; the compiler still constructs the handler as a local at the call site and passes it by reference without the caller writing `ref` — this is the standard interpolated-string-handler-conversion behavior for `ref`/`in`/`out` handler parameters.

#### `<PropertyName>` format tags

An interpolation hole's format can start with an "html-like" tag to *also* capture that value as a structured property: `$"Hello, {name:<UserName>}!"` appends `name` to the message text (using whatever format follows the tag, if any) and adds a `"UserName"` structured property with `name`'s raw (unformatted) value. `$"[{ts:<Timestamp>HH:mm:ss}]"` formats `ts` with `"HH:mm:ss"` in the message while capturing the raw `DateTime` under `"Timestamp"`. An empty tag (`<>`) opts out of capturing while still stripping itself out, so a real format that happens to start with `<` can be written as `<>therealformat`. A tag name starting with `@` (e.g. `<@UserId>`, or `<@>` to destructure without renaming) additionally renders the value into the *message* using Serilog-style destructured formatting instead of `IFormattable`/`ToString()` — any format text following such a tag is parsed but ignored, since destructured rendering replaces ordinary formatting entirely. Destructuring itself is implemented in `LogPropertyDestructuring.cs`: objects render as `TypeName { Prop1: Value1, ... }` (anonymous types omit the type name), collections as `[item1, item2]`, dictionaries as `{ [key1]: value1, ... }`, strings/chars are quoted, other scalars render unquoted via invariant-culture `IFormattable`/`ToString()`; recursion is depth-bounded, collections/dictionaries are capped per `MaxCollectionItems`, and reference cycles render `<circular reference>` instead of recursing forever. Parsing lives in `LogPropertyTagFormat.cs` (hand-authored, not generated — this is genuine parsing logic, not mechanical repetition):

- Fast path: if `format` is null/empty or doesn't start with `<`, return immediately — no allocation, not even a dictionary lookup.
- Tag path: format specifiers in interpolated strings are always compile-time literals (and therefore interned — the same literal text is always the same `string` instance process-wide), so the parsed `(PropertyName, Format)` result is cached in a `ConcurrentDictionary<string, TagFormat>` keyed by that literal reference. This is safe to cache unboundedly (unlike MEL's message-template cache) because the key space is bounded by the number of distinct tag literals actually written in source, not by runtime-constructed strings.
- Each handler struct's `AppendFormatted<T>(T value, [int alignment,] string? format)` overloads parse the tag, lazily allocate a `List<KeyValuePair<string, object?>>?` field on first capture (stays `null`, zero-alloc, if no tag is ever used), and pass the *stripped* remaining format on to `DefaultInterpolatedStringHandler` for the message text.
- `LogPropertiesState`/`LogPropertiesState<T1..T6>` were extended with an `explicitProperties` slot alongside the statically-typed property arguments (`property1..T6` for the generic overloads, the collection list for the non-generic one). For the plain (non-collection) overloads that slot is populated directly from the handler's `GetCapturedProperties()`; for the collection-parameter overloads it's a `ConcatPropertyList` of the caller-supplied collection followed by the tag-captured properties. `Count`/the indexer address that slot first, then the statically-typed properties — no list concatenation beyond the single `ConcatPropertyList` wrapper, just index arithmetic.

### Source layout for the API surface

- `LogInterpolatedStringHandlers.g.cs` — the 7 handler structs (one per level + `WriteInterpolatedStringHandler` for `Write`). Nearly identical bodies; kept as 7 separate concrete types (rather than one generic type) because `InterpolatedStringHandlerArgumentAttribute` can only bind constructor parameters to actual method parameters, and the level-specific methods (`Debug`, `Information`, ...) don't have a `LogLevel` parameter to bind to — each handler type hardcodes its own level instead. Each wraps a `System.Runtime.CompilerServices.DefaultInterpolatedStringHandler` field (invariant culture) and delegates `AppendLiteral`/`AppendFormatted` straight to it — that type already implements pooled-buffer building, `IFormattable`/`ISpanFormattable` dispatch, and alignment padding correctly, so there's no need to hand-roll it. Because `DefaultInterpolatedStringHandler` is itself a ref struct, these wrapper types must be `ref struct` too (and *not* `readonly struct` — a readonly struct defensively copies mutable-struct fields on every method call, which would silently make `Append*` mutate a throwaway copy instead of the real field).
- `LogPropertiesState.g.cs` — `LogPropertiesState<T1..T6>` (internal), one generic arity per file section. Each closed generic instantiation gets its own `static readonly Func<TState, Exception?, string> Formatter` field, which the CLR caches per-instantiation for free — this is what replaces `Microsoft.Extensions.Logging`'s fragile format-string-keyed formatter cache (the thing that made non-constant message templates a performance foot-gun in the original MEL extension methods).
- `StructuredLoggerExtensions.g.cs` — the 784 extension methods.
- `LogPropertiesState.cs` — the non-generic state type backing the 0-arity overloads (with or without the leading collection parameter).
- `ConcatPropertyList.cs` — zero-copy `IReadOnlyList<KeyValuePair<string, object?>>` adapter that concatenates two lists without copying; used by the collection-parameter overloads to combine the caller-supplied collection (first) with tag-captured properties (second) before handing them to `LogPropertiesState`/`LogPropertiesState<T1..T6>`.
- `LogPropertyTagFormat.cs` — parses `<PropertyName>format` (and `<@PropertyName>`-destructuring) tags out of a format string; see below.
- `LogPropertyDestructuring.cs` — renders a value as Serilog-style destructured text for the `<@PropertyName>` tag format; see below.

All three `*.g.cs` files are produced by `eng/GenerateSource.cs`, a .NET 10 file-based app (no `.csproj`; run directly via `dotnet run eng/GenerateSource.cs`). The generated files are checked into source control like ordinary source — re-run the generator and commit the diff after changing anything in `eng/GenerateSource.cs` (e.g. to change the max generic arity, add a level, etc.). The generator also emits XML doc comments for every public generated member (mechanically derived from level/arity/EventId-Exception-combo, e.g. "Writes a log message with 2 structured properties at the Debug level."); `GenerateDocumentationFile` is on with no `CS1591` suppression, so a missing doc comment on any public member fails the build with a warning-as-visible signal (not error) the next time source changes.

### The analyzers (`src/RandomSkunk.StructuredLogging.Analyzers/`)

Five diagnostics, `RSSL0001`–`RSSL0005`, all defined in `DiagnosticDescriptors.cs`:

- **RSSL0001** (`AvoidLoggerExtensionsAnalyzer`/`AvoidLoggerExtensionsCodeFixProvider`, Info) — flags calls to `Microsoft.Extensions.Logging.LoggerExtensions`' `Log`/`LogTrace`/`LogDebug`/`LogInformation`/`LogWarning`/`LogError`/`LogCritical`, which force structured properties into the message template, and offers a fix (`LoggerExtensionsMigration`) converting to the corresponding RandomSkunk.StructuredLogging call.
- **RSSL0002** (`LogPropertyTagFormatAnalyzer`/`LogPropertyTagFormatCodeFixProvider`, Hidden) — anchors on an interpolation hole that *already* uses the `<PropertyName>` tag format; its fix (`RemoveLogPropertyTagFormatMigration`) strips the tag back to a plain hole.
- **RSSL0003** (`NonCapturingInterpolationHoleAnalyzer`/`NonCapturingInterpolationHoleCodeFixProvider`, Hidden) — the mirror image of RSSL0002: anchors on a hole that does *not* use the tag format; its fix (`AddLogPropertyTagFormatMigration`) adds one, guessing a property name via `PropertyNameGuessing` (always falls back to a generic placeholder, since the guess only seeds a tag the developer can rename).
- **RSSL0004** (`LogPropertyTupleArgumentAnalyzer`/`LogPropertyTupleArgumentCodeFixProvider`, Hidden) — anchors on a trailing `("Name", value)` tuple argument whose name is a compile-time-constant string (per the broader "constant" notion in `ConstantStringExpressionParsing.cs`, which also covers interpolated strings whose holes are themselves constant); its fix (`MoveLogPropertyTupleArgumentMigration`) moves it into a `<PropertyName>` tag on an interpolation hole instead.
- **RSSL0005** (`StructuredLoggerExtensionsInvocationAnalyzer`/`StructuredLoggerExtensionsInvocationCodeFixProvider`, Hidden) — anchors on *any* call to a RandomSkunk.StructuredLogging extension method regardless of overload; its fix (`StructuredLoggerExtensionsInvocationMigration`) converts back to the corresponding `Microsoft.Extensions.Logging` call, using `PropertyNameGuessing` for property names read from source (no generic fallback here — a wrong/generic name would become a permanent, visible part of the message template).

RSSL0002–RSSL0005 are all `Hidden`-severity by design: they don't flag anything wrong with the code, they exist purely as anchor locations so their paired code fixes can be invoked from an IDE. `PropertyNameGuessing.cs` and `ConstantStringExpressionParsing.cs` are shared helpers, not tied to one analyzer. `AnalyzerReleases.Shipped.md`/`AnalyzerReleases.Unshipped.md` track the required Roslyn analyzer-release-tracking metadata for these five IDs.

## Operation logging

A second, hand-written (not generated) feature living alongside the structured-logging extension methods: a way to journal everything that happens during an operation (and arbitrarily nested sub-operations) and flush it as exactly *one* log entry when the operation completes, inspired by canonical log lines / wide events. All operation-logging types live in the `RandomSkunk.StructuredLogging.Operation` namespace and the `src/RandomSkunk.StructuredLogging/Operation/` folder — a caller needs `using RandomSkunk.StructuredLogging.Operation;` in addition to the base namespace to use them. Entry point: `logger.BeginOperation("name")` (`LoggerOperationExtensions.cs`) returns an `IOperationLog`; disposing it writes the single log entry. `IOperationLog.BeginSubOperation("name")` returns a nested `IOperationLog` (the interface is unified — no separate sub-operation type), which only ever appends to the same root journal/state — a sub-operation never writes its own log entry.

### API shape

- `IOperationLog` (`IOperationLog.cs`) — `Properties` (the `AddProperty` entries added so far, as `IReadOnlyList<KeyValuePair<string, object?>>`), `EventId` (the `EventId` the operation was begun with, or `default`), `IsEnabled` (whether the operation is actually journaling - `false` if the level given to `BeginOperation` was disabled at that time; never changes afterward, and `Escalate` can never turn a disabled operation into an enabled one), `AddProperty<T>(name, value)` (adds an unprefixed structured property to the eventual entry), `Append(text)` (journal line), `AppendValue<T>(value, [CallerArgumentExpression] valueName)` (journal line `` `valueName`: value `` via `IFormattable`/`ToString()`), `AppendJson<T>(value, valueName)` (same but value rendered as indented JSON), `BeginSubOperation(name)`, `SetException(exception)`, `SetResult<T>(value)`, `Escalate(level)` (raises the level the final entry is written at if `level` is more severe than the operation's current level, otherwise a no-op; never re-enables an operation whose level was disabled up front at `BeginOperation`). All fluent members (all except `Properties`/`EventId`/`IsEnabled`) return `IOperationLog`. Root vs. sub-operation behavior differs per-member at the implementation level (see below), not via separate interfaces: on a sub-operation, `SetException`/`SetResult` write journal lines instead of setting root-level structured properties (a sub-operation never gets its own `Operation.Result`, and its exception never becomes the root's `Exception`). `Properties`, `EventId`, `IsEnabled`, and the level `Escalate` affects are the same across the root and every sub-operation, since they all contribute to the one eventual entry; each level's own `name` (passed to `BeginOperation`/`BeginSubOperation`) is used in that level's journal lines but isn't exposed back through the interface.
- `LoggerOperationExtensions.BeginOperation` — two overloads (`(logger, name, level, threadSafe)` and `(logger, eventId, name, level, threadSafe)`, `eventId` first after `logger`, both default `level: LogLevel.Information`, `threadSafe: false`). Checks `logger.IsEnabled(level)` up front; if disabled, returns a `DisabledOperationLog` (optionally wrapped in `SynchronizedOperationLog` when `threadSafe: true`) instead of allocating an `OperationLogState`/`RootOperationLog`.
- `OperationLogExtensions.cs` — three chainable, non-interface extension methods for use inline in expressions: `T.RecordValueTo(log, [CallerArgumentExpression] valueName)`, `T.RecordJsonTo(log, valueName)`, `T.RecordResultTo(log)`, each `[return: NotNullIfNotNull]` and returning the value unchanged so they can be chained onto a `return` expression, e.g. `return order.RecordResultTo(log);`.

### Implementation (`Operation/`)

- `OperationLogState.cs` — the mutable state shared by a root operation and every sub-operation nested under it (`Logger`, `Level`, `EventId`, `StartTime`, `Stopwatch`, pooled `Journal` `StringBuilder`, pooled `Properties` list, `Result`/`HasResult`/`Exception`). The constructor writes the journal's header - an `Operation: {name}` line, an `EventId: {eventId}` line (only when `eventId != default`), and a `Start Time: {StartTime:yyyy-MM-dd HH:mm:ss.fff zzz}` line, followed by a dashed rule sized to the longest header line - before starting the `Stopwatch`. No journal entry is written for operation start; the first entry is whatever the caller appends first. `BeginJournalEntry()` (called by every subsequent journal write) appends a newline then delegates to the same `AppendTimestamp` helper for the `[elapsed-seconds]` prefix (total seconds, 3 decimals, formatted via `stackalloc` + `TryFormat` with `CultureInfo.InvariantCulture` — no string allocation and no dependence on the current thread's culture). Callers append the rest of the entry's content directly to the returned `StringBuilder`. `RootOperationLog.DisposeCore()` writes the final journal line as `` `[elapsed] Operation complete.` `` — the elapsed time comes from the shared `[elapsed]` prefix rather than being repeated in the message text.
- `OperationLog<TSelf>` (`OperationLog.cs`) — internal abstract base class for `RootOperationLog`/`ChildOperationLog`, holding the members whose implementations are identical between the two (`AddProperty`, `Escalate`, `Append`, `AppendValue`, `AppendJson`, `BeginSubOperation`, and a thread-safe-via-`Interlocked.Exchange` `Dispose()` that calls the abstract `DisposeCore()`). `TSelf : OperationLog<TSelf>, IOperationLog` lets these shared members return the concrete derived type via `(TSelf)this` without each derived class redeclaring them.
- `RootOperationLog.cs` / `ChildOperationLog.cs` — the real (non-thread-safe) `IOperationLog` implementations, both deriving from `OperationLog<TSelf>` and only implementing `SetException`, `SetResult`, and `DisposeCore`. `RootOperationLog.DisposeCore()` is the *only* place that ever calls `state.Logger.Write(...)`; the completed journal text is passed as the plain `string message` argument itself (not a structured property), `state.Properties` (each `AddProperty` entry, lazily allocated) is passed as the leading collection argument, and `Operation.StartTime`/`Operation.DurationSeconds` (an unrounded `double`) are trailing tuple arguments; `Operation.Name` and (when `SetResult` was called) `Operation.Result` are added to `state.Properties` directly before writing. Returns the pooled `Journal` back to `OperationLogPools`, then writes. `ChildOperationLog` only ever appends to the shared `state.Journal`; its `DisposeCore()` appends a "`` `Name` complete. ``" line.
- `DisabledOperationLog.cs` — `IOperationLog` returned for a disabled logger; `EventId` and `AddProperty`/`Properties` behave normally, since callers may read them regardless of whether the operation logs anything, `IsEnabled` is hardcoded `false`, and every other member is a no-op. Holds `eventId` and a lazily-allocated `List<KeyValuePair<string, object?>>?` properties field directly - since `IOperationLog` no longer exposes a per-level `name`, a root and every sub-operation begun from it are behaviorally identical, so `BeginSubOperation` just returns `this` instead of allocating. Not a singleton (unlike the type it replaced) since it still carries per-operation state (`EventId`/`Properties`).
- `SynchronizedOperationLog.cs` — opt-in (`threadSafe: true`) decorator wrapping an inner `IOperationLog` (root or sub-operation); every member `lock`s a shared `gate` object before delegating to `inner`, and `BeginSubOperation` wraps the resulting sub-operation in another `SynchronizedOperationLog` sharing the same `gate`. The whole operation tree — root plus every nested sub-operation, however deep — shares exactly *one* gate.
- `ValueFormatting.cs` — `Format<T>` (the `IFormattable`/`ToString()`-based rendering used by `AppendValue`/`SetResult`) and `AppendJson<T>(StringBuilder, T)`, which serializes `value` to UTF-8 via a pooled `Utf8JsonWriter`/`ArrayBufferWriter<byte>` (`PooledJsonWriter.cs`, indented) and transcodes those bytes directly into the target `StringBuilder` using `ArrayPool<char>`-rented buffers — the JSON text is never materialized as its own `string`.
- `ObjectPool.cs` / `OperationLogPools.cs` — a minimal `ConcurrentBag<T>`-backed pool (`Rent`/`Return`, `factory`/`reset`/`shouldPool` delegates) used for `Journals` (pooled `StringBuilder`s, retained only if `Capacity <= 4096`) and `JsonWriters` (pooled `PooledJsonWriter`s, retained only if `Capacity <= 16384`). `state.Properties` is not pooled — it's a plain `List<KeyValuePair<string, object?>>?`, left `null` (zero-alloc) until the first `AddProperty` call. `ObjectPool<T>.MaxSize` (`Environment.ProcessorCount * 4`) additionally caps `_items.Count`, checked before the pricier `shouldPool` predicate, so no single pool can grow unbounded under heavy concurrency regardless of what `shouldPool` would otherwise allow.

Design notes worth remembering: the feature is **not thread-safe by default** — call sites that need concurrent access (e.g. sub-operations run via `Task.WhenAll`) must pass `threadSafe: true` to `BeginOperation` to get the `SynchronizedOperationLog` decorator. Root vs. sub-operation asymmetry is real, not just naming: only the root ever writes a log entry, whose message is the completed journal text, or gets an `Operation.Name`/`Operation.Result`/`Operation.StartTime`/`Operation.DurationSeconds` set of structured properties; sub-operations only ever contribute journal text.
