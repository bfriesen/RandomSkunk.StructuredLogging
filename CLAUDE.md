# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

RandomSkunk.StructuredLogging: modern structured logging extensions for .NET that separate human-readable messages from machine-readable attributes. It replaces `Microsoft.Extensions.Logging.Abstractions`'s `LogDebug`/`LogInformation`/etc. extension methods, which force every structured property into the message template. This library lets a message be formatted however the caller wants while structured properties are attached separately and explicitly.

## Environment

This is a WSL environment with no Linux .NET SDK installed. Use the Windows SDK via `cmd.exe`, e.g.:

```bash
cmd.exe /c "dotnet build"
cmd.exe /c "dotnet test"
```

The SDK version is pinned in `global.json` (currently 10.0.301).

### The public API shape

`StructuredLoggerExtensions` (generated) exposes, for each of `Trace`/`Debug`/`Information`/`Warning`/`Error`/`Critical`, plus a level-as-argument `Write`:

- 4 `EventId`/`Exception` combinations (both, `EventId` only, `Exception` only, neither)
- × 7 structured-property shapes: no properties, generic arity 1–6 via `(string Name, T1 Value) logProperty1, ...` (avoids boxing for small property counts). There's no arbitrary-count `params` overload — a caller with more than 6 statically-known properties builds a collection instead.
- × 2 collection variants: each of the 7 shapes above also has a sibling overload with a leading `IReadOnlyCollection<KeyValuePair<string, object?>> logProperties` parameter immediately after `this ILogger logger` (accepts a previously constructed `Dictionary<string, object?>` or `List<KeyValuePair<string, object?>>`), letting a caller combine that collection with statically-known properties in the same call. The generated body does `logProperties as IReadOnlyList<...> ?? logProperties.ToArray()`, so a `List` is used as-is and a `Dictionary` is copied once per call (measured: 96 B/op vs 40 B for a 2-entry collection — exactly one `24 + 2×16` array). **That eager copy is deliberate; don't try to make it lazy.** Every alternative is worse for a library that can't know how its sink reads the state: caching a lazily-materialized array needs somewhere to put it, and `LogPropertiesState` is a readonly struct passed by value through `Log<TState>` — a cache field only sticks once a sink boxes it, and MEL hands the state to each provider separately, so several providers would each box and each materialize. Making it reliable means allocating a holder per log call, i.e. charging every caller to spare `Dictionary` callers. Enumerating to position *i* in the indexer instead avoids the holder but is worse where it matters: a 7-entry dictionary read by an index-based sink becomes ~28 enumerator steps and 7 boxed enumerators, several hundred bytes against the 96 it was trying to save, and O(n²) for anything larger. And there is no waste to remove in the first place — `Enumerable.ToArray` takes the `ICollection<T>.CopyTo` path, so it is already a single allocation with no enumerator and no growth. The cost is bounded, predictable, paid only by callers who chose a non-list collection, and avoidable by passing a `List` (noted in the README).
- × 2 message-parameter shapes: every combination above is generated twice, once with the message parameter typed as the level's `[InterpolatedStringHandler]` struct and once typed as plain `string`.

= 784 methods total.

The interpolated-handler message parameter is a custom `[InterpolatedStringHandler]` struct (one per level, plus a level-generic one for `Write`). Its constructor checks `logger.IsEnabled(level)`, stores the result in an internal `IsEnabled` property, and — if disabled — sets `handlerIsValid = false`, so the C# compiler skips evaluating the interpolation holes entirely (they're never appended, never formatted); `logger.Debug($"... {ExpensiveCall()}")` doesn't call `ExpensiveCall()` when the Debug level is disabled. The generated extension method then checks the handler's `IsEnabled` property rather than calling `logger.IsEnabled(level)` a second time — the handler already has the answer, so a handler-message overload only ever dispatches to `ILogger.IsEnabled` once (a plain-`string message` overload, having no handler, still calls it directly). There is no implicit conversion from `string` to the handler type; instead, a separate `string message` overload exists for every combination, so a plain string argument (constant or not) binds directly to it — no handler construction, no formatting work, just an explicit `IsEnabled` check before logging. Per the C# spec's interpolated-string betterness rule, an interpolated string literal (`$"..."`) still prefers the handler overload over the `string` overload when both are applicable, so `logger.Debug($"literal")` gets the handler's tag-capturing behavior while `logger.Debug(someStringVariable)` gets the plain overload. The handler-typed `message` parameter is declared `ref` (e.g. `ref DebugInterpolatedStringHandler message`) to avoid copying the ref struct (which embeds a `DefaultInterpolatedStringHandler`, itself a ref struct) into the callee; the compiler still constructs the handler as a local at the call site and passes it by reference without the caller writing `ref` — this is the standard interpolated-string-handler-conversion behavior for `ref`/`in`/`out` handler parameters.

#### `<PropertyName>` format tags

An interpolation hole's format can start with an "html-like" tag to *also* capture that value as a structured property: `$"Hello, {name:<UserName>}!"` appends `name` to the message text (using whatever format follows the tag, if any) and adds a `"UserName"` structured property with `name`'s raw (unformatted) value. `$"[{ts:<Timestamp>HH:mm:ss}]"` formats `ts` with `"HH:mm:ss"` in the message while capturing the raw `DateTime` under `"Timestamp"`. An empty tag (`<>`) opts out of capturing while still stripping itself out, so a real format that happens to start with `<` can be written as `<>therealformat`. A format that starts with `<` but never closes (`{userId:<UserId}`) is a missing-`>` typo rather than a real format: `LogPropertyTagFormat` throws the public `UnterminatedLogPropertyTagException` (a `FormatException` subclass, declared in `LogPropertyTagFormat.cs`) instead of passing the raw text along as a format string, and RSSL0008 flags the same mistake at compile time. A tag name starting with `@` (e.g. `<@UserId>`, or `<@>` to destructure without renaming) additionally requests Serilog-style destructured capture. If no format follows such a tag, the value is also rendered into the *message* using destructured formatting instead of `IFormattable`/`ToString()`; if a format does follow the tag (e.g. `<@Amount>F3`), that format is honored for the message exactly as an ordinary `<PropertyName>` tag would be — destructuring then only affects how the property is captured, not how the message looks. Either way, a captured property name gets an `@` prefix (e.g. `@UserId`) to signal the destructuring request to a Serilog-style sink; an empty destructuring tag (`<@>`) never captures anything regardless of a trailing format, the same as a plain `<>`. Destructured message rendering itself is implemented in `LogPropertyDestructuring.cs` (whose `AppendDestructured` renders straight into the message handler, chunk by chunk, rather than building an intermediate `string`; the `Render` overload that does return a `string` survives only for the alignment case, where padding needs contiguous text): objects render as `TypeName { Prop1: Value1, ... }` (anonymous types omit the type name), collections as `[item1, item2]`, dictionaries as `{ [key1]: value1, ... }`, strings/chars are quoted, other scalars render unquoted via invariant-culture `IFormattable`/`ToString()`; recursion is depth-bounded, collections/dictionaries are capped per `MaxCollectionItems`, and reference cycles render `<circular reference>` instead of recursing forever. Its scratch `StringBuilder` and its cycle-tracking ancestor stack are both `[ThreadStatic]` and reused across renders, detached on rent so a reentrant render (a property getter that itself logs) gets its own — deliberately *not* an `ObjectPool`, since a `ConcurrentBag` rent/return pair costs more than rendering a small value does, which made pooling a net latency loss on the most common values. The ancestor stack is a `List<object>` scanned linearly rather than a `HashSet`: it never holds more than `MaxDepth` entries, and comparing that many references beats hashing one. Parsing lives in `LogPropertyTagFormat.cs` (hand-authored, not generated — this is genuine parsing logic, not mechanical repetition):

- Fast path: if `format` is null/empty or doesn't start with `<`, return immediately — no allocation, not even a dictionary lookup.
- Tag path: format specifiers in interpolated strings are always compile-time literals (and therefore interned — the same literal text is always the same `string` instance process-wide), so the parsed `(PropertyName, Format)` result is cached in a `ConcurrentDictionary<string, TagFormat>` keyed by that literal reference. This is safe to cache unboundedly (unlike MEL's message-template cache) because the key space is bounded by the number of distinct tag literals actually written in source, not by runtime-constructed strings.
- Each handler struct's `AppendFormatted<T>(T value, [int alignment,] string? format)` overloads parse the tag, lazily allocate a `List<KeyValuePair<string, object?>>?` field on first capture (stays `null`, zero-alloc, if no tag is ever used), constructed with `capacity: 2` rather than left to `List`'s default 0→4→8 growth. A message that captures anything at all almost always captures one or two properties, and both fit in a 2-slot array (56 bytes) instead of the default's 4-slot first allocation (88 bytes). Capturing three or more pays 56 bytes for the abandoned 2-slot array, so this is a bet on the distribution of capture counts, not a free win — it comes out ahead as long as fewer than ~36% of capturing calls capture 3+. Deliberately a constant rather than being derived from `formattedCount`: sizing to the hole count would make a message with many holes but one tag *worse* than the default, and would cost a field on every handler to carry the count to the first capture, and pass the *stripped* remaining format on to `DefaultInterpolatedStringHandler` for the message text.
- `LogPropertiesState<T1..T6>` carries two interface-typed slots alongside the statically-typed property arguments (`property1..T6`): `logProperties` (the caller-supplied collection, or `Array.Empty<...>()` for the non-collection overloads) and `capturedProperties` (the handler's `GetCapturedProperties()`, or `Array.Empty<...>()` for the plain-`string`-message overloads). `Count`/the indexer address `logProperties` first, then `capturedProperties`, then the statically-typed properties, via index arithmetic — no list concatenation and no wrapper type. Both slots are always reference-typed (a `List<T>` or `Array.Empty<T>()`), so passing them through the interface-typed constructor parameters never boxes.

### Source layout for the API surface

- `LogInterpolatedStringHandlers.g.cs` — the 7 handler structs (one per level + `WriteInterpolatedStringHandler` for `Write`). Nearly identical bodies; kept as 7 separate concrete types (rather than one generic type) because `InterpolatedStringHandlerArgumentAttribute` can only bind constructor parameters to actual method parameters, and the level-specific methods (`Debug`, `Information`, ...) don't have a `LogLevel` parameter to bind to — each handler type hardcodes its own level instead. Each wraps a `System.Runtime.CompilerServices.DefaultInterpolatedStringHandler` field (invariant culture) and delegates `AppendLiteral`/`AppendFormatted` straight to it — that type already implements pooled-buffer building, `IFormattable`/`ISpanFormattable` dispatch, and alignment padding correctly, so there's no need to hand-roll it. Because `DefaultInterpolatedStringHandler` is itself a ref struct, these wrapper types must be `ref struct` too (and *not* `readonly struct` — a readonly struct defensively copies mutable-struct fields on every method call, which would silently make `Append*` mutate a throwaway copy instead of the real field).
- `LogPropertiesState.g.cs` — `LogPropertiesState<T1..T6>` (internal), one generic arity per file section. Each closed generic instantiation gets its own `static readonly Func<TState, Exception?, string> Formatter` field, which the CLR caches per-instantiation for free — this is what replaces `Microsoft.Extensions.Logging`'s fragile format-string-keyed formatter cache (the thing that made non-constant message templates a performance foot-gun in the original MEL extension methods).
- `StructuredLoggerExtensions.g.cs` — the 784 extension methods.
- `LogPropertiesState.cs` — the non-generic state type backing the 0-arity overloads (with or without the leading collection parameter); its two interface-typed slots (`logProperties`, `capturedProperties`) serve the same role, and are addressed in the same order, as `LogPropertiesState<T1..T6>`'s. That ordering is load-bearing and must stay in lockstep across every arity: it used to address `capturedProperties` first here while every generic arity addressed `logProperties` first, so adding a single per-call property to a call that combined a collection with a `<PropertyName>` tag silently swapped those two groups — flipping duplicate-key precedence for any sink that resolves by first- or last-wins. `eng/GenerateSource.cs` now builds the constructor arguments for all arities from one expression so the two can't drift apart again.
- `LogPropertyTagFormat.cs` — parses `<PropertyName>format` (and `<@PropertyName>`-destructuring) tags out of a format string; see below.
- `LogPropertyDestructuring.cs` — renders a value as Serilog-style destructured text for the `<@PropertyName>` tag format; see below.

All three `*.g.cs` files are produced by `eng/GenerateSource.cs`, a .NET 10 file-based app (no `.csproj`; run directly via `dotnet run eng/GenerateSource.cs`). The generated files are checked into source control like ordinary source — re-run the generator and commit the diff after changing anything in `eng/GenerateSource.cs` (e.g. to change the max generic arity, add a level, etc.). The generator also emits XML doc comments for every public generated member (mechanically derived from level/arity/EventId-Exception-combo, e.g. "Writes a log message with 2 structured properties at the Debug level."); `GenerateDocumentationFile` is on with no `CS1591` suppression, so a missing doc comment on any public member fails the build with a warning-as-visible signal (not error) the next time source changes.

### The analyzers (`src/RandomSkunk.StructuredLogging.Analyzers/`)

Ten diagnostics, `RSSL0001`–`RSSL0010`, all defined in `DiagnosticDescriptors.cs`. They fall into two groups, and the distinction matters: the first group flags nothing wrong, the second flags real bugs.

**Anchor diagnostics (`Usage` category).** RSSL0001 is `Info`; RSSL0002–RSSL0005 are `Hidden` by design — they don't flag anything wrong with the code, they exist purely as anchor locations so their paired code fixes can be invoked from an IDE.

- **RSSL0001** (`AvoidLoggerExtensionsAnalyzer`/`AvoidLoggerExtensionsCodeFixProvider`, Info) — flags calls to `Microsoft.Extensions.Logging.LoggerExtensions`' `Log`/`LogTrace`/`LogDebug`/`LogInformation`/`LogWarning`/`LogError`/`LogCritical`, which force structured properties into the message template, and offers a fix (`LoggerExtensionsMigration`) converting to the corresponding RandomSkunk.StructuredLogging call.
- **RSSL0002** (`LogPropertyTagFormatAnalyzer`/`LogPropertyTagFormatCodeFixProvider`, Hidden) — anchors on an interpolation hole that *already* uses the `<PropertyName>` tag format. Two fixes: `LogPropertyTagFormatMigration` moves the hole out of the message into a trailing `("Name", value)` tuple argument, and `RemoveLogPropertyTagFormatMigration` strips the tag back to a plain hole.
- **RSSL0003** (`NonCapturingInterpolationHoleAnalyzer`/`NonCapturingInterpolationHoleCodeFixProvider`, Hidden) — the mirror image of RSSL0002: anchors on a hole that does *not* use the tag format; its fix (`AddLogPropertyTagFormatMigration`) adds one, guessing a property name via `PropertyNameGuessing` (always falls back to a generic placeholder, since the guess only seeds a tag the developer can rename).
- **RSSL0004** (`LogPropertyTupleArgumentAnalyzer`/`LogPropertyTupleArgumentCodeFixProvider`, Hidden) — anchors on a trailing `("Name", value)` tuple argument whose name is a compile-time-constant string (per the broader "constant" notion in `ConstantStringExpressionParsing.cs`, which also covers interpolated strings whose holes are themselves constant); its fix (`MoveLogPropertyTupleArgumentMigration`) moves it into a `<PropertyName>` tag on an interpolation hole instead.
- **RSSL0005** (`StructuredLoggerExtensionsInvocationAnalyzer`/`StructuredLoggerExtensionsInvocationCodeFixProvider`, Hidden) — anchors on *any* call to a RandomSkunk.StructuredLogging extension method regardless of overload; its fix (`StructuredLoggerExtensionsInvocationMigration`) converts back to the corresponding `Microsoft.Extensions.Logging` call, using `PropertyNameGuessing` for property names read from source (no generic fallback here — a wrong/generic name would become a permanent, visible part of the message template).

**Real-defect diagnostics (`Reliability` category).** These flag genuine bugs and are on by default. Only RSSL0006 ships a code fix; RSSL0007–RSSL0010 are analyzer-only, since the remedy is always "pass the interpolated string directly to the logging call" and the right edit depends on what the surrounding code was trying to do.

- **RSSL0006** (`UndisposedOperationLogAnalyzer`/`UndisposedOperationLogCodeFixProvider`, Warning) — flags a `BeginOperation`/`BeginSubOperation` call whose returned `IOperationLog` isn't visibly disposed (a `using` declaration/statement, an explicit `Dispose()`, or returning/assigning it for someone else to dispose; passing it as a plain method argument doesn't count). Forgetting to dispose silently drops the entire journal — not even a partial entry is written. CA2000 can't catch this itself: its escape analysis anchors on `new`-expressions and can't see through `BeginOperation`'s object construction inside the already-compiled library assembly. Offers two fixes — `AddUsingDeclarationMigration` and `AddUsingBlockMigration` (the block form leaves the body empty rather than guessing which surrounding statements belong inside it) — both only when the call is a whole statement or a single-variable declaration's initializer. `OperationLogChain.cs` lets the analyzer and both fixes reason about fluent chains (`logger.BeginOperation("Op").AddProperty(...)`), whose outermost link is still that same undisposed log.
- **RSSL0007** (`InterpolatedStringLocalMessageAnalyzer`, Warning) — the message argument is a local initialized from a tag-capturing interpolated string: `string msg = $"User {id:<UserId>}"; logger.Debug(msg);`.
- **RSSL0008** (`UnterminatedLogPropertyTagAnalyzer`, **Error**) — an interpolation hole whose format starts with `<` but has no matching `>` (`{userId:<UserId}`, a missing-`>` typo). Error severity because it always indicates a bug; at run time the same mistake throws `UnterminatedLogPropertyTagException` rather than silently treating the raw text as a format string. A real format that must start with `<` uses the `<>` escape hatch instead.
- **RSSL0009** (`InterpolatedStringMessageExpressionAnalyzer`, Warning) — a method call or `+` concatenation applied directly to a tag-capturing interpolated literal: `logger.Debug($"User {id:<UserId>}".ToUpper())`.
- **RSSL0010** (`InterpolatedStringHelperMethodArgumentAnalyzer`, Warning) — a tag-capturing literal passed through some other wrapper/helper method first: `logger.Debug(FormatMessage($"User {id:<UserId>}"))`.

RSSL0007/RSSL0009/RSSL0010 are three faces of one failure, which is why their descriptors read almost identically: each forces the call to bind the plain `string message` overload instead of the interpolated-string-handler overload, so the message is built eagerly regardless of level *and* the `<PropertyName>` tag reaches the value's `IFormattable.ToString(format)` as a genuine .NET format string — usually throwing `FormatException` the first time that path runs. All three fire only when a tag is actually at stake (shared detection in `InterpolatedStringTagFormatDetection.cs`); a tagless literal merely loses the disabled-level optimization, which they deliberately don't police.

Shared helpers, not tied to one analyzer: `PropertyNameGuessing.cs`, `ConstantStringExpressionParsing.cs`, `LogPropertyTagFormatParsing.cs` (mirrors the tag-detection half of the runtime's own `LogPropertyTagFormat.cs`, which this netstandard2.0-only project can't reference directly), `InterpolatedStringTagFormatDetection.cs`, `OperationLogChain.cs`, and `OperationLogFixHelpers.cs`. `AnalyzerReleases.Shipped.md`/`AnalyzerReleases.Unshipped.md` track the required Roslyn analyzer-release-tracking metadata for all ten IDs.

## Operation logging

A second, hand-written (not generated) feature living alongside the structured-logging extension methods: a way to journal everything that happens during an operation (and arbitrarily nested sub-operations) and flush it as exactly *one* log entry when the operation completes, inspired by canonical log lines / wide events. All operation-logging types live in the `RandomSkunk.StructuredLogging.Operation` namespace and the `src/RandomSkunk.StructuredLogging/Operation/` folder — a caller needs `using RandomSkunk.StructuredLogging.Operation;` in addition to the base namespace to use them. Entry point: `logger.BeginOperation("name")` (`LoggerOperationExtensions.cs`) returns an `IOperationLog`; disposing it writes the single log entry. `IOperationLog.BeginSubOperation("name")` returns a nested `IOperationLog` (the interface is unified — no separate sub-operation type), which only ever appends to the same root journal/state — a sub-operation never writes its own log entry.

### API shape

- `IOperationLog` (`IOperationLog.cs`) — `Properties` (the `AddProperty` entries added so far, as `IReadOnlyList<KeyValuePair<string, object?>>`), `EventId` (the `EventId` the operation was begun with, or `default`), `IsEnabled` (whether the operation is actually journaling - `false` if the level given to `BeginOperation` was disabled at that time; never changes afterward, and `Escalate` can never turn a disabled operation into an enabled one), `AddProperty<T>(name, value)` (adds an unprefixed structured property to the eventual entry), `Append(text)` (journal line; also an interpolated-handler overload, see below), `AppendValue<T>(value, [CallerArgumentExpression] valueName)` (journal line `` `valueName`: value `` via `IFormattable`/`ToString()`), `AppendJson<T>(value, valueName)` (same but value rendered as indented JSON), `BeginSubOperation(name)` (also an interpolated-handler overload), `SetException(exception)`, `SetResult<T>(value)`, `Escalate(level)` (raises the level the final entry is written at if `level` is more severe than the operation's current level, otherwise a no-op; never re-enables an operation whose level was disabled up front at `BeginOperation`; when it actually raises the level, also appends a journal line - `"Operation escalated from {previous} to {level}."` on the root, `` "`{name}` escalated from {previous} to {level}." `` on a sub-operation - so the final entry's level is self-explanatory from the journal text). All fluent members (all except `Properties`/`EventId`/`IsEnabled`) return `IOperationLog`. Root vs. sub-operation behavior differs per-member at the implementation level (see below), not via separate interfaces: on a sub-operation, `SetException`/`SetResult` write journal lines instead of setting root-level structured properties (a sub-operation never gets its own `Operation.Result`, and its exception never becomes the root's `Exception`). `Properties`, `EventId`, `IsEnabled`, and the level `Escalate` affects are the same across the root and every sub-operation, since they all contribute to the one eventual entry; each level's own `name` (passed to `BeginOperation`/`BeginSubOperation`) is used in that level's journal lines but isn't exposed back through the interface.
- `OperationLogInterpolatedStringHandler.cs` — the `[InterpolatedStringHandler]` behind `Append`/`BeginSubOperation`'s handler overloads (bound to the receiving `IOperationLog` via `[InterpolatedStringHandlerArgument("")]`). Its constructor checks `log.IsEnabled` and, if disabled, skips evaluating the interpolation holes entirely - mirroring the structured-logging message handlers. When enabled, it targets a `StringBuilder` to write straight into: the real journal directly, if `log` implements the internal `IJournalOwner` (`RootOperationLog`/`ChildOperationLog`, via `OperationLog<TSelf>`), or otherwise a private buffer rented from `OperationLogPools.Journals` (in practice, whenever `log` is a `SynchronizedOperationLog` - writing into the *shared* journal has to happen under its lock, which this handler can't hold: its constructor and `AppendFormatted` calls all run during argument evaluation, before `Append`/`BeginSubOperation`'s method body - and any lock taken inside it - ever runs; a hole that throws with the lock already held would leave it deadlocked forever, so the handler never takes it, and writes into a private, thread-local buffer instead - a throw there only discards that one pooled buffer). `OperationLog<TSelf>.Append(ref handler)` is then a no-op (the handler already wrote the whole entry); its `BeginSubOperation(ref handler)` slices the interpolated name back out of the journal (`journal.ToString(start, length)`, then `Insert`s the wrapping backtick and appends "` started.`") since, unlike `Append`'s text, the name is also stored (`_operationName`) for reuse in later journal lines. `SynchronizedOperationLog`'s two overloads splice the rented buffer into `inner`'s real journal (or call `inner`'s string-parameter overload directly) under `gate`, then return the buffer to the pool via a `finally`.
- `LoggerOperationExtensions.BeginOperation` — two overloads (`(logger, name, level, threadSafe)` and `(logger, eventId, name, level, threadSafe)`, `eventId` first after `logger`, both default `level: LogLevel.Information`, `threadSafe: false`). Checks `logger.IsEnabled(level)` up front; if disabled, returns a `DisabledOperationLog` (optionally wrapped in `SynchronizedOperationLog` when `threadSafe: true`) instead of allocating an `OperationLogState`/`RootOperationLog`.
- `OperationLogExtensions.cs` — three chainable, non-interface extension methods for use inline in expressions: `T.RecordValueTo(log, [CallerArgumentExpression] valueName)`, `T.RecordJsonTo(log, valueName)`, `T.RecordResultTo(log)`, each `[return: NotNullIfNotNull]` and returning the value unchanged so they can be chained onto a `return` expression, e.g. `return order.RecordResultTo(log);`.

### Implementation (`Operation/`)

- `OperationLogState.cs` — the mutable state shared by a root operation and every sub-operation nested under it (`Logger`, `Level`, `EventId`, `StartTime`, `Stopwatch`, pooled `Journal` `StringBuilder`, pooled `Properties` list, `Result`/`HasResult`/`Exception`). The constructor writes the journal's header - an `Operation: {name}` line, an `EventId: {eventId}` line (only when `eventId != default`), and a `Start Time: {StartTime:yyyy-MM-dd HH:mm:ss.fff zzz}` line, followed by a dashed rule sized to the longest header line - before starting the `Stopwatch`. Each line is appended straight to the journal and measured in place (a line's length is just how far the journal grew while writing it), so none of them - including the `EventId` line, which spells out `EventId.ToString()`'s `Name ?? Id.ToString(InvariantCulture)` rather than calling it - is ever materialized as its own string just to size the rule. No journal entry is written for operation start; the first entry is whatever the caller appends first. `BeginJournalEntry()` (called by every subsequent journal write) appends a newline then delegates to the same `AppendTimestamp` helper for the `[elapsed-seconds]` prefix (total seconds, 3 decimals, formatted via `stackalloc` + `TryFormat` with `CultureInfo.InvariantCulture` — no string allocation and no dependence on the current thread's culture). Callers append the rest of the entry's content directly to the returned `StringBuilder`. `RootOperationLog.DisposeCore()` writes the final journal line as `` `[elapsed] Operation complete.` `` — the elapsed time comes from the shared `[elapsed]` prefix rather than being repeated in the message text.
- `OperationLog<TSelf>` (`OperationLog.cs`) — internal abstract base class for `RootOperationLog`/`ChildOperationLog`, holding the members whose implementations are identical between the two (`AddProperty`, `Append`, `AppendValue`, `AppendJson`, `BeginSubOperation`, and a thread-safe-via-`Interlocked.Exchange` `Dispose()` that calls the abstract `DisposeCore()`). `TSelf : OperationLog<TSelf>, IOperationLog` lets these shared members return the concrete derived type via `(TSelf)this` without each derived class redeclaring them. Also implements `IJournalOwner`'s single member, `BeginJournalEntry()` (throws if disposed, then delegates to `OperationLogState.BeginJournalEntry()`) - the other `Append`/`AppendValue`/`AppendJson`/`BeginSubOperation(string)` members all route through it rather than calling `_state` directly, so the disposed-check stays in one place. `Escalate` is *not* here, despite being identical in spirit across root/sub-operation - the journal message it appends differs (see below), so it's declared separately on `RootOperationLog`/`ChildOperationLog`, same as `SetException`/`SetResult`.
- `RootOperationLog.cs` / `ChildOperationLog.cs` — the real (non-thread-safe) `IOperationLog` implementations, both deriving from `OperationLog<TSelf>` and implementing `SetException`, `SetResult`, `Escalate`, and `DisposeCore`. `RootOperationLog.DisposeCore()` is the *only* place that ever calls `state.Logger.Write(...)`; the completed journal text is passed as the plain `string message` argument itself (not a structured property), `state.Properties` (each `AddProperty` entry, lazily allocated) is passed as the leading collection argument, and `Operation.StartTime`/`Operation.DurationSeconds` (an unrounded `double`) are trailing tuple arguments; `Operation.Name` and (when `SetResult` was called) `Operation.Result` are added to `state.Properties` directly before writing. Returns the pooled `Journal` back to `OperationLogPools`, then writes. `ChildOperationLog` only ever appends to the shared `state.Journal`; its `DisposeCore()` appends a "`` `Name` complete. ``" line. Both `Escalate` implementations call `OperationLogState.Escalate(level)` (which now returns the *previous* `Level`, not `void`) and only append a journal line - `"Operation escalated from {previous} to {level}."` / `` "`{name}` escalated from {previous} to {level}." `` - when `level` was actually more severe than the previous level; `ThrowIfDisposed()` still runs unconditionally first, matching the member's documented exception contract even for a no-op escalation.
- `DisabledOperationLog.cs` — `IOperationLog` returned for a disabled logger; `EventId` and `AddProperty`/`Properties` behave normally, since callers may read them regardless of whether the operation logs anything, `IsEnabled` is hardcoded `false`, and every other member is a no-op. Holds `eventId` and a lazily-allocated `List<KeyValuePair<string, object?>>?` properties field directly - since `IOperationLog` no longer exposes a per-level `name`, a root and every sub-operation begun from it are behaviorally identical, so `BeginSubOperation` just returns `this` instead of allocating. Not a singleton (unlike the type it replaced) since it still carries per-operation state (`EventId`/`Properties`).
- `SynchronizedOperationLog.cs` — opt-in (`threadSafe: true`) decorator wrapping an inner `IOperationLog` (root or sub-operation); every member `lock`s a shared `gate` object before delegating to `inner`, and `BeginSubOperation` wraps the resulting sub-operation in another `SynchronizedOperationLog` sharing the same `gate`. The whole operation tree — root plus every nested sub-operation, however deep — shares exactly *one* gate. Deliberately does not implement `IJournalOwner` - see `OperationLogInterpolatedStringHandler.cs` above for why.
- `IJournalOwner.cs` — internal marker interface (`BeginJournalEntry(): StringBuilder`) implemented only by `OperationLog<TSelf>`, letting `OperationLogInterpolatedStringHandler` write directly into a real journal when one is safely available and fall back to a pooled private buffer otherwise.
- `ValueFormatting.cs` — `AppendValue<T>(StringBuilder, T)` (the `IFormattable`/`ToString()`-based rendering used by `AppendValue`/`SetResult`, appending straight to the journal rather than returning a `string`: an `ISpanFormattable` value - every built-in numeric type, `DateTime`, `Guid`, ... - is formatted directly into the journal's current chunk, so nothing is rendered as its own string on the way in; a `null` value, or one whose `ToString()` returns `null`, still reads as the literal `null`) and `AppendJson<T>(StringBuilder, T)`, which serializes `value` to UTF-8 via a pooled `Utf8JsonWriter`/`ArrayBufferWriter<byte>` (`PooledJsonWriter.cs`, indented) and transcodes those bytes directly into the target `StringBuilder` using `ArrayPool<char>`-rented buffers — the JSON text is never materialized as its own `string`.
- `ObjectPool.cs` / `OperationLogPools.cs` — a minimal `ConcurrentBag<T>`-backed pool (`Rent`/`Return`, `factory`/`reset`/`shouldPool` delegates) used for `Journals` (pooled `StringBuilder`s, retained only if `Capacity <= 4096`) and `JsonWriters` (pooled `PooledJsonWriter`s, retained only if `Capacity <= 16384`). `state.Properties` is not pooled — it's a plain `List<KeyValuePair<string, object?>>?`, left `null` (zero-alloc) until the first `AddProperty` call. `ObjectPool<T>.MaxSize` (`Environment.ProcessorCount * 4`) additionally caps the pool's size, checked before the pricier `shouldPool` predicate, so no single pool can grow unbounded under heavy concurrency regardless of what `shouldPool` would otherwise allow. That size is tracked in an `Interlocked` counter field rather than read from `ConcurrentBag<T>.Count`, which freezes the bag (global lock plus every per-thread queue lock) and therefore serializes every `Return` — measured at ~6x throughput loss on the `threadSafe: true` path, where `Journals` sees a rent/return per `Append` instead of one per operation. `Journals` now also backs `OperationLogInterpolatedStringHandler`'s private buffers (rented per `Append`/`BeginSubOperation` call on a `SynchronizedOperationLog`, not just once per operation), so it sees more rent/return churn on the `threadSafe: true` path than before.

Design notes worth remembering: the feature is **not thread-safe by default** — call sites that need concurrent access (e.g. sub-operations run via `Task.WhenAll`) must pass `threadSafe: true` to `BeginOperation` to get the `SynchronizedOperationLog` decorator. Root vs. sub-operation asymmetry is real, not just naming: only the root ever writes a log entry, whose message is the completed journal text, or gets an `Operation.Name`/`Operation.Result`/`Operation.StartTime`/`Operation.DurationSeconds` set of structured properties; sub-operations only ever contribute journal text.
