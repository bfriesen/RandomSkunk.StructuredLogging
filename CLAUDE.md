# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

RandomSkunk.StructuredLogging: modern structured logging extensions for .NET that separate human-readable messages from machine-readable attributes. It replaces `Microsoft.Extensions.Logging.Abstractions`'s `LogDebug`/`LogInformation`/etc. extension methods, which force every structured property into the message template. This library lets a message be formatted however the caller wants while structured properties are attached separately and explicitly.

## Environment

This is a WSL environment with no Linux .NET SDK installed. Use the Windows SDK via `cmd.exe`, e.g.:

```bash
cmd.exe /c "dotnet build"
cmd.exe /c "dotnet test"
```

The SDK version is pinned in `global.json` (currently 10.0.301).

### The public API shape

`StructuredLoggerExtensions` (generated) exposes, for each of `Trace`/`Debug`/`Information`/`Warning`/`Error`/`Critical`, plus a level-as-argument `Write`:

- 4 `EventId`/`Exception` combinations (both, `EventId` only, `Exception` only, neither)
- × 7 structured-property shapes: no properties, generic arity 1–6 via `(string Name, T1 Value) logProperty1, ...` (avoids boxing for small property counts). There's no arbitrary-count `params` overload — a caller with more than 6 statically-known properties builds a collection instead.
- × 2 collection variants: each of the 7 shapes above also has a sibling overload with a leading `IReadOnlyCollection<KeyValuePair<string, object?>> logProperties` parameter immediately after `this ILogger logger` (accepts a previously constructed `Dictionary<string, object?>` or `List<KeyValuePair<string, object?>>`), letting a caller combine that collection with statically-known properties in the same call. The generated body does `logProperties as IReadOnlyList<...> ?? logProperties.ToArray()`, so a `List` is used as-is and a `Dictionary` is copied once per call. **That eager copy is deliberate; don't try to make it lazy** — every lazy alternative is worse for a library that can't know how its sink reads the state. The full reasoning is in the comment above the emit site in `eng/GenerateSource.cs`; read it before touching this.
- × 2 message-parameter shapes: every combination above is generated twice, once with the message parameter typed as the level's `[InterpolatedStringHandler]` struct and once typed as plain `string`.

= 784 methods total.

The interpolated-handler message parameter is a custom `[InterpolatedStringHandler]` struct (one per level, plus a level-generic one for `Write`). Its constructor checks `logger.IsEnabled(level)`, stores the result in an internal `IsEnabled` property, and — if disabled — sets `handlerIsValid = false`, so the C# compiler skips evaluating the interpolation holes entirely (they're never appended, never formatted); `logger.Debug($"... {ExpensiveCall()}")` doesn't call `ExpensiveCall()` when the Debug level is disabled. The generated extension method then checks the handler's `IsEnabled` property rather than calling `logger.IsEnabled(level)` a second time — the handler already has the answer, so a handler-message overload only ever dispatches to `ILogger.IsEnabled` once (a plain-`string message` overload, having no handler, still calls it directly). There is no implicit conversion from `string` to the handler type; instead, a separate `string message` overload exists for every combination, so a plain string argument (constant or not) binds directly to it — no handler construction, no formatting work, just an explicit `IsEnabled` check before logging. Per the C# spec's interpolated-string betterness rule, an interpolated string literal (`$"..."`) still prefers the handler overload over the `string` overload when both are applicable, so `logger.Debug($"literal")` gets the handler's tag-capturing behavior while `logger.Debug(someStringVariable)` gets the plain overload. The handler-typed `message` parameter is declared `ref` (e.g. `ref DebugInterpolatedStringHandler message`) to avoid copying the ref struct (which embeds a `DefaultInterpolatedStringHandler`, itself a ref struct) into the callee; the compiler still constructs the handler as a local at the call site and passes it by reference without the caller writing `ref` — this is the standard interpolated-string-handler-conversion behavior for `ref`/`in`/`out` handler parameters.

#### `<PropertyName>` format tags

An interpolation hole's format can start with an "html-like" tag to *also* capture that value as a structured property: `$"Hello, {name:<UserName>}!"` puts `name` in the message text and captures its raw value under `"UserName"`. README §2 has the full syntax with examples; the parts worth knowing up front are the traps. An empty tag (`<>`) opts out of capturing while stripping itself, so a real format starting with `<` is written `<>therealformat`. A format that starts with `<` and never closes (`{userId:<UserId}`) is a typo, not a format: `LogPropertyTagFormat` throws the public `UnterminatedLogPropertyTagException` rather than passing the raw text through, and RSSL0008 catches it at compile time. A `@`-prefixed tag (`<@UserId>`, or `<@>`) requests Serilog-style destructured capture, and the captured key gets an `@` prefix to signal that to the sink. Two easily-missed rules there: a format *following* a destructuring tag (`<@Amount>F3`) is honored for the message exactly as an ordinary tag would be — destructuring then affects only capture, not the message; and `<@>` never captures anything regardless of a trailing format, same as a plain `<>`. Destructured rendering itself lives in `LogPropertyDestructuring.cs` (depth-bounded, collection-capped, cycle-safe; its buffer and ancestor-stack choices are explained in comments there). Parsing lives in `LogPropertyTagFormat.cs` (hand-authored, not generated — genuine parsing logic, not mechanical repetition):

- Fast path: if `format` is null/empty or doesn't start with `<`, return immediately — no allocation, not even a dictionary lookup.
- Tag path: format specifiers in interpolated strings are always compile-time literals (and therefore interned — the same literal text is always the same `string` instance process-wide), so the parsed `(PropertyName, Format)` result is cached in a `ConcurrentDictionary<string, TagFormat>` keyed by that literal reference. This is safe to cache unboundedly (unlike MEL's message-template cache) because the key space is bounded by the number of distinct tag literals actually written in source, not by runtime-constructed strings.
- Each handler struct's `AppendFormatted<T>(T value, [int alignment,] string? format)` overloads parse the tag, lazily allocate a `List<KeyValuePair<string, object?>>?` field on first capture (stays `null`, zero-alloc, if no tag is ever used), constructed with `capacity: 2` rather than left to `List`'s default 0→4→8 growth — a bet on the distribution of capture counts, not a free win, and deliberately a constant rather than derived from `formattedCount` (reasoning in the comment at that emit site in `eng/GenerateSource.cs`). The *stripped* remaining format is passed on to `DefaultInterpolatedStringHandler` for the message text.
- `LogPropertiesState<T1..T6>` carries two interface-typed slots alongside the statically-typed property arguments (`property1..T6`): `logProperties` (the caller-supplied collection, or `Array.Empty<...>()` for the non-collection overloads) and `capturedProperties` (the handler's `GetCapturedProperties()`, or `Array.Empty<...>()` for the plain-`string`-message overloads). `Count`/the indexer address `logProperties` first, then `capturedProperties`, then the statically-typed properties, via index arithmetic — no list concatenation and no wrapper type. Both slots are always reference-typed (a `List<T>` or `Array.Empty<T>()`), so passing them through the interface-typed constructor parameters never boxes.

### Source layout for the API surface

- `LogInterpolatedStringHandlers.g.cs` — the 7 handler structs (one per level + `WriteInterpolatedStringHandler` for `Write`). Nearly identical bodies; kept as 7 separate concrete types (rather than one generic type) because `InterpolatedStringHandlerArgumentAttribute` can only bind constructor parameters to actual method parameters, and the level-specific methods (`Debug`, `Information`, ...) don't have a `LogLevel` parameter to bind to — each handler type hardcodes its own level instead. Each wraps a `System.Runtime.CompilerServices.DefaultInterpolatedStringHandler` field (invariant culture) and delegates `AppendLiteral`/`AppendFormatted` straight to it — that type already implements pooled-buffer building, `IFormattable`/`ISpanFormattable` dispatch, and alignment padding correctly, so there's no need to hand-roll it. Because `DefaultInterpolatedStringHandler` is itself a ref struct, these wrapper types must be `ref struct` too (and *not* `readonly struct` — a readonly struct defensively copies mutable-struct fields on every method call, which would silently make `Append*` mutate a throwaway copy instead of the real field).
- `LogPropertiesState.g.cs` — `LogPropertiesState<T1..T6>` (internal), one generic arity per file section. Each closed generic instantiation gets its own `static readonly Func<TState, Exception?, string> Formatter` field, which the CLR caches per-instantiation for free — this is what replaces `Microsoft.Extensions.Logging`'s fragile format-string-keyed formatter cache (the thing that made non-constant message templates a performance foot-gun in the original MEL extension methods).
- `StructuredLoggerExtensions.g.cs` — the 784 extension methods.
- `LogPropertiesState.cs` — the non-generic state type backing the 0-arity overloads (with or without the leading collection parameter); its two interface-typed slots (`logProperties`, `capturedProperties`) serve the same role, and are addressed in the same order, as `LogPropertiesState<T1..T6>`'s. That ordering is load-bearing and must stay in lockstep across every arity: it used to address `capturedProperties` first here while every generic arity addressed `logProperties` first, so adding a single per-call property to a call that combined a collection with a `<PropertyName>` tag silently swapped those two groups — flipping duplicate-key precedence for any sink that resolves by first- or last-wins. `eng/GenerateSource.cs` now builds the constructor arguments for all arities from one expression so the two can't drift apart again.
- `LogPropertyTagFormat.cs` — parses `<PropertyName>format` (and `<@PropertyName>`-destructuring) tags out of a format string; see below.
- `LogPropertyDestructuring.cs` — renders a value as Serilog-style destructured text for the `<@PropertyName>` tag format; see below.

All three `*.g.cs` files are produced by `eng/GenerateSource.cs`, a .NET 10 file-based app (no `.csproj`; run directly via `dotnet run eng/GenerateSource.cs`). The generated files are checked into source control like ordinary source — re-run the generator and commit the diff after changing anything in `eng/GenerateSource.cs` (e.g. to change the max generic arity, add a level, etc.). The generator also emits XML doc comments for every public generated member (mechanically derived from level/arity/EventId-Exception-combo, e.g. "Writes a log message with 2 structured properties at the Debug level."); `GenerateDocumentationFile` is on with no `CS1591` suppression, so a missing doc comment on any public member fails the build with a warning-as-visible signal (not error) the next time source changes.

### The analyzers (`src/RandomSkunk.StructuredLogging.Analyzers/`)

Ten diagnostics, `RSSL0001`–`RSSL0010`, all defined in `DiagnosticDescriptors.cs`. They fall into two groups, and the distinction matters: the first group flags nothing wrong, the second flags real bugs.

**Anchor diagnostics (`Usage` category).** RSSL0001 is `Info`; RSSL0002–RSSL0005 are `Hidden` by design — they don't flag anything wrong with the code, they exist purely as anchor locations so their paired code fixes can be invoked from an IDE.

- **RSSL0001** (`AvoidLoggerExtensionsAnalyzer`/`AvoidLoggerExtensionsCodeFixProvider`, Info) — flags calls to `Microsoft.Extensions.Logging.LoggerExtensions`' `Log`/`LogTrace`/`LogDebug`/`LogInformation`/`LogWarning`/`LogError`/`LogCritical`, which force structured properties into the message template, and offers a fix (`LoggerExtensionsMigration`) converting to the corresponding RandomSkunk.StructuredLogging call.
- **RSSL0002** (`LogPropertyTagFormatAnalyzer`/`LogPropertyTagFormatCodeFixProvider`, Hidden) — anchors on an interpolation hole that *already* uses the `<PropertyName>` tag format. Two fixes: `LogPropertyTagFormatMigration` moves the hole out of the message into a trailing `("Name", value)` tuple argument, and `RemoveLogPropertyTagFormatMigration` strips the tag back to a plain hole.
- **RSSL0003** (`NonCapturingInterpolationHoleAnalyzer`/`NonCapturingInterpolationHoleCodeFixProvider`, Hidden) — the mirror image of RSSL0002: anchors on a hole that does *not* use the tag format; its fix (`AddLogPropertyTagFormatMigration`) adds one, guessing a property name via `PropertyNameGuessing` (always falls back to a generic placeholder, since the guess only seeds a tag the developer can rename).
- **RSSL0004** (`LogPropertyTupleArgumentAnalyzer`/`LogPropertyTupleArgumentCodeFixProvider`, Hidden) — anchors on a trailing `("Name", value)` tuple argument whose name is a compile-time-constant string (per the broader "constant" notion in `ConstantStringExpressionParsing.cs`, which also covers interpolated strings whose holes are themselves constant); its fix (`MoveLogPropertyTupleArgumentMigration`) moves it into a `<PropertyName>` tag on an interpolation hole instead.
- **RSSL0005** (`StructuredLoggerExtensionsInvocationAnalyzer`/`StructuredLoggerExtensionsInvocationCodeFixProvider`, Hidden) — anchors on *any* call to a RandomSkunk.StructuredLogging extension method regardless of overload; its fix (`StructuredLoggerExtensionsInvocationMigration`) converts back to the corresponding `Microsoft.Extensions.Logging` call, using `PropertyNameGuessing` for property names read from source (no generic fallback here — a wrong/generic name would become a permanent, visible part of the message template).

**Real-defect diagnostics (`Reliability` category).** These flag genuine bugs and are on by default. Only RSSL0006 ships a code fix; RSSL0007–RSSL0010 are analyzer-only, since the remedy is always "pass the interpolated string directly to the logging call" and the right edit depends on what the surrounding code was trying to do.

- **RSSL0006** (`UndisposedOperationLogAnalyzer`/`UndisposedOperationLogCodeFixProvider`, Warning) — flags a `BeginOperation`/`BeginSubOperation` call whose returned `IOperationLog` isn't visibly disposed (a `using` declaration/statement, an explicit `Dispose()`, or returning/assigning it for someone else to dispose; passing it as a plain method argument doesn't count). Forgetting to dispose silently drops the entire journal — not even a partial entry is written. CA2000 can't catch this itself: its escape analysis anchors on `new`-expressions and can't see through `BeginOperation`'s object construction inside the already-compiled library assembly. Offers two fixes — `AddUsingDeclarationMigration` and `AddUsingBlockMigration` (the block form leaves the body empty rather than guessing which surrounding statements belong inside it) — both only when the call is a whole statement or a single-variable declaration's initializer. `OperationLogChain.cs` lets the analyzer and both fixes reason about fluent chains (`logger.BeginOperation("Op").AddProperty(...)`), whose outermost link is still that same undisposed log.
- **RSSL0007** (`InterpolatedStringLocalMessageAnalyzer`, Warning) — the message argument is a local initialized from a tag-capturing interpolated string: `string msg = $"User {id:<UserId>}"; logger.Debug(msg);`.
- **RSSL0008** (`UnterminatedLogPropertyTagAnalyzer`, **Error**) — an interpolation hole whose format starts with `<` but has no matching `>` (`{userId:<UserId}`, a missing-`>` typo). Error severity because it always indicates a bug; at run time the same mistake throws `UnterminatedLogPropertyTagException` rather than silently treating the raw text as a format string. A real format that must start with `<` uses the `<>` escape hatch instead.
- **RSSL0009** (`InterpolatedStringMessageExpressionAnalyzer`, Warning) — a method call or `+` concatenation applied directly to a tag-capturing interpolated literal: `logger.Debug($"User {id:<UserId>}".ToUpper())`.
- **RSSL0010** (`InterpolatedStringHelperMethodArgumentAnalyzer`, Warning) — a tag-capturing literal passed through some other wrapper/helper method first: `logger.Debug(FormatMessage($"User {id:<UserId>}"))`.

RSSL0007/RSSL0009/RSSL0010 are three faces of one failure, which is why their descriptors read almost identically: each forces the call to bind the plain `string message` overload instead of the interpolated-string-handler overload, so the message is built eagerly regardless of level *and* the `<PropertyName>` tag reaches the value's `IFormattable.ToString(format)` as a genuine .NET format string — usually throwing `FormatException` the first time that path runs. All three fire only when a tag is actually at stake (shared detection in `InterpolatedStringTagFormatDetection.cs`); a tagless literal merely loses the disabled-level optimization, which they deliberately don't police.

Shared helpers, not tied to one analyzer: `PropertyNameGuessing.cs`, `ConstantStringExpressionParsing.cs`, `LogPropertyTagFormatParsing.cs` (mirrors the tag-detection half of the runtime's own `LogPropertyTagFormat.cs`, which this netstandard2.0-only project can't reference directly), `InterpolatedStringTagFormatDetection.cs`, `OperationLogChain.cs`, and `OperationLogFixHelpers.cs`. `AnalyzerReleases.Shipped.md`/`AnalyzerReleases.Unshipped.md` track the required Roslyn analyzer-release-tracking metadata for all ten IDs.

## Operation logging

A second, hand-written (not generated) feature living alongside the structured-logging extension methods: a way to journal everything that happens during an operation (and arbitrarily nested sub-operations) and flush it as exactly *one* log entry when the operation completes, inspired by canonical log lines / wide events. All operation-logging types live in the `RandomSkunk.StructuredLogging.Operation` namespace and the `src/RandomSkunk.StructuredLogging/Operation/` folder — a caller needs `using RandomSkunk.StructuredLogging.Operation;` in addition to the base namespace to use them. Entry point: `logger.BeginOperation("name")` (`LoggerOperationExtensions.cs`) returns an `IOperationLog`; disposing it writes the single log entry. `IOperationLog.BeginSubOperation("name")` returns a nested `ISubOperationLog`, which only ever appends to the same root journal/state — a sub-operation never writes its own log entry.

### API shape

- `IOperationLogBase<TSelf>` (`IOperationLogBase.cs`) — public generic interface declaring every member shared between the root and every sub-operation: `Properties`, `EventId`, `IsEnabled`, `Escalate`, `AddProperty`, `Append`/`AppendValue`/`AppendJson`, `AppendException`/`AppendResult` (below), and `BeginSubOperation` (which always returns `ISubOperationLog`, regardless of `TSelf`). Every other fluent member returns `TSelf` itself, constrained `where TSelf : IOperationLogBase<TSelf>`. `IOperationLog` (`IOperationLog.cs`) and `ISubOperationLog` (`ISubOperationLog.cs`) each extend `IOperationLogBase<TSelf>` closed over themselves (`IOperationLog : IOperationLogBase<IOperationLog>`, `ISubOperationLog : IOperationLogBase<ISubOperationLog>`) - deliberately *not* related to each other (neither extends the other), so a chain of calls on an `IOperationLog` keeps returning `IOperationLog` (and likewise for `ISubOperationLog`) rather than widening to a shared ancestor, and so `IOperationLog`'s extra `SetException`/`SetResult` (below) can never be reached from a sub-operation reference.
- `IOperationLog` adds `SetException`/`SetResult`, which set the `Exception`/`Operation.Result` of the one eventual log entry and append a one-line journal marker recording when that happened (and whether it overwrote an earlier call — see `RootOperationLog.cs` below). A sub-operation reference can never reach in and overwrite the root's exception or result — that's a compile error, not a runtime footgun. To do that from inside a sub-operation, hold onto the root `IOperationLog` itself (not the sub-operation) and call `SetException`/`SetResult` on it directly.
- `AppendException`/`AppendResult` (declared on `IOperationLogBase<TSelf>`, so both root and sub-operation have them) append a `"`name` failed: ..."`/`"`name` result: ..."` journal line describing the value — the root's own versions write `"Operation failed: ..."`/`"Operation result: ..."` instead, since it has no sub-operation name of its own. Neither ever touches the root's `Exception`/`Operation.Result` structured properties — only `IOperationLog.SetException`/`SetResult` do that.
- `Properties`, `EventId`, `IsEnabled`, and the level `Escalate` affects are shared across the root and every sub-operation, since they all feed the one eventual entry. Each level's own `name` is used in that level's journal lines but isn't exposed back through either interface. `IsEnabled` is fixed at `BeginOperation` time and never changes: `Escalate` can raise the level but can never re-enable a disabled operation.
- `OperationLogInterpolatedStringHandler.cs` — the `[InterpolatedStringHandler]` behind `Append`/`BeginSubOperation`'s handler overloads. Has *two* constructors, one per receiver type (`IOperationLog`, `ISubOperationLog`) - since the two interfaces are unrelated, the interpolated-string-handler pattern (which binds a constructor overload to the receiver's exact static type via `[InterpolatedStringHandlerArgument("")]`) needs one for each; both just forward to a shared private constructor after pulling out the two things that differ per receiver (`IsEnabled`, and whether it's an `IJournalOwner`). Its constructor checks `log.IsEnabled` and, if disabled, skips evaluating the interpolation holes entirely - mirroring the structured-logging message handlers. When enabled, it targets a `StringBuilder` to write straight into: the real journal directly, if `log` implements the internal `IJournalOwner` (`RootOperationLog`/`ChildOperationLog`, via `OperationLog<TSelf>`), or otherwise a private buffer rented from `OperationLogPools.Journals` (in practice, whenever `log` is a `SynchronizedOperationLog`/`SynchronizedSubOperationLog` - writing into the *shared* journal has to happen under its lock, which this handler can't hold: its constructor and `AppendFormatted` calls all run during argument evaluation, before `Append`/`BeginSubOperation`'s method body - and any lock taken inside it - ever runs; a hole that throws with the lock already held would leave it deadlocked forever, so the handler never takes it, and writes into a private, thread-local buffer instead - a throw there only discards that one pooled buffer). `OperationLog<TSelf>.Append(ref handler)` is then a no-op (the handler already wrote the whole entry); its `BeginSubOperation(ref handler)` slices the interpolated name back out of the journal (`journal.ToString(start, length)`, then `Insert`s the wrapping backtick and appends "` started.`") since, unlike `Append`'s text, the name is also stored (`_operationName`) for reuse in later journal lines. `SynchronizedOperationLogBase<TInner>`'s two overloads splice the rented buffer into `_inner`'s real journal (or call `_inner`'s string-parameter overload directly) under `_gate`, then return the buffer to the pool via a `finally`.
- `LoggerOperationExtensions.BeginOperation` — two overloads (`(logger, name, level, threadSafe)` and `(logger, eventId, name, level, threadSafe)`, `eventId` first after `logger`, both default `level: LogLevel.Information`, `threadSafe: false`). Checks `logger.IsEnabled(level)` up front; if disabled, returns a `DisabledOperationLog` (optionally wrapped in `SynchronizedOperationLog` when `threadSafe: true`) instead of allocating an `OperationLogState`/`RootOperationLog`.
- `OperationLogExtensions.cs` — five chainable, non-interface extension methods for use inline in expressions, each named after the `IOperationLogBase<TSelf>`/`IOperationLog` member it calls, plus a `To` suffix: `T.AppendValueTo(log, [CallerArgumentExpression] valueName)`, `T.AppendJsonTo(log, valueName)`, `T.AddPropertyTo(log, propertyName)`, and `T.AppendResultTo(log)` (calls `AppendResult`) are all generic over a second `TLog` type parameter constrained to `IOperationLogBase<TLog>`, so one method works for either an `IOperationLog` or an `ISubOperationLog` `log` argument (needed precisely because the two interfaces are unrelated - a non-generic `ISubOperationLog log` parameter would otherwise reject an `IOperationLog` argument). `T.SetResultTo(log)` (calls `SetResult`) is the one exception - it takes a plain `IOperationLog`, since `SetResult` only exists there. Each is `[return: NotNullIfNotNull]` and returns the value unchanged so it can be chained onto a `return` expression, e.g. `return order.SetResultTo(log);` (root) or `return allocation.AppendResultTo(subLog);` (sub-operation).

### Implementation (`Operation/`)

- `OperationLogState.cs` — the mutable state shared by a root operation and every sub-operation nested under it (`Logger`, `Level`, `EventId`, `StartTime`, `Stopwatch`, pooled `Journal` `StringBuilder`, pooled `Properties` list, `Result`/`HasResult`/`Exception`). The constructor writes the journal's header - an `Operation: {name}` line, an `Event Id: {eventId}` line (only when `eventId != default`), and a `Start Time: {StartTime:yyyy-MM-dd HH:mm:ss.fff zzz}` line, followed by a dashed rule sized to the longest header line - before starting the `Stopwatch`. Each line is appended straight to the journal and measured in place (a line's length is just how far the journal grew while writing it), so none of them - including the `Event Id` line, which spells out `EventId.ToString()`'s `Name ?? Id.ToString(InvariantCulture)` rather than calling it - is ever materialized as its own string just to size the rule. No journal entry is written for operation start; the first entry is whatever the caller appends first. `BeginJournalEntry()` (called by every subsequent journal write) appends a newline then delegates to the same `AppendTimestamp` helper for the `[elapsed-seconds]` prefix (total seconds, 3 decimals, formatted via `stackalloc` + `TryFormat` with `CultureInfo.InvariantCulture` — no string allocation and no dependence on the current thread's culture). Callers append the rest of the entry's content directly to the returned `StringBuilder`. `RootOperationLog.DisposeCore()` writes the final journal line as `` `[elapsed] Operation complete.` `` — the elapsed time comes from the shared `[elapsed]` prefix rather than being repeated in the message text.
- `OperationLog<TSelf>` (`OperationLog.cs`) — internal abstract base class for `RootOperationLog`/`ChildOperationLog`, holding the members whose implementations are identical between the two (`AddProperty`, `Append`, `AppendValue`, `AppendJson`, `BeginSubOperation`, and a thread-safe-via-`Interlocked.Exchange` `Dispose()` that calls the abstract `DisposeCore()`). Here `TSelf` is the *interface* the concrete derived class implements (`IOperationLog` for `RootOperationLog`, `ISubOperationLog` for `ChildOperationLog`) rather than the concrete class itself, constrained `where TSelf : class, IOperationLogBase<TSelf>` - the shared members return `TSelf` directly via `(TSelf)(object)this` (the `(object)` step is required: a class-to-type-parameter cast needs it when the type parameter's only constraint is an interface, unlike the old CRTP-style `where TSelf : OperationLog<TSelf>` constraint, which let `(TSelf)this` work directly) without each derived class redeclaring them. Also implements `IJournalOwner`'s single member, `BeginJournalEntry()` (throws if disposed, then delegates to `OperationLogState.BeginJournalEntry()`) - the other `Append`/`AppendValue`/`AppendJson`/`BeginSubOperation(string)` members all route through it rather than calling `_state` directly, so the disposed-check stays in one place. `Escalate`, `AppendException`, and `AppendResult` are *not* here, despite being identical in spirit across root/sub-operation - the journal message each appends differs (see below), so they're declared separately on `RootOperationLog`/`ChildOperationLog`, same as the root-only `SetException`/`SetResult`.
- `RootOperationLog.cs` — the real (non-thread-safe) `IOperationLog` implementation, deriving from `OperationLog<IOperationLog>` and implementing `SetException`, `SetResult`, `AppendException`, `AppendResult`, `Escalate`, and `DisposeCore`. `SetException`/`SetResult` set `state.Exception`/`state.Result` (+`HasResult`) directly, and also append a one-line journal marker — `"Operation exception set."`/`"Operation result set."` on the first call, `"Operation exception set again, overwriting the previous value."`/`"Operation result set again, overwriting the previous value."` on any later call (detected by checking `state.Exception is not null`/`state.HasResult` *before* overwriting) — without duplicating the exception's text or the result's formatted value in the journal; `AppendException`/`AppendResult` are the journal-only counterparts, writing `"Operation failed: ..."`/`"Operation result: ..."` lines (with the full exception/formatted value) and never touching `state.Exception`/`state.Result`. `DisposeCore()` is the *only* place that ever calls `state.Logger.Write(...)`; the completed journal text is passed as the plain `string message` argument itself (not a structured property), and `Operation.Name`/`Operation.StartTime`/`Operation.DurationSeconds` (an unrounded `double`) are trailing tuple arguments; (when `SetResult` was called) `Operation.Result` is added to `state.Properties` directly before writing, which is then passed as the leading collection argument. Returns the pooled `Journal` back to `OperationLogPools`, then writes.
- `ChildOperationLog.cs` — the real (non-thread-safe) `ISubOperationLog` implementation for a sub-operation, deriving from `OperationLog<ISubOperationLog>` and implementing `AppendException`, `AppendResult`, `Escalate`, and `DisposeCore`. Never implements `IOperationLog` - a sub-operation is only ever handed out as an `ISubOperationLog`. Every member only ever appends to the shared `state.Journal`; its `AppendException`/`AppendResult` write `` "`{name}` failed: ..." ``/`` "`{name}` result: ..." `` lines, and its `DisposeCore()` appends a "`` `Name` complete. ``" line. Both `RootOperationLog.Escalate` and `ChildOperationLog.Escalate` call `OperationLogState.Escalate(level)` (which returns the *previous* `Level`, not `void`) and only append a journal line - `"Operation escalated from {previous} to {level}."` / `` "`{name}` escalated from {previous} to {level}." `` - when `level` was actually more severe than the previous level; `ThrowIfDisposed()` still runs unconditionally first, matching the member's documented exception contract even for a no-op escalation.
- `DisabledOperationLog.cs` — implements *both* `IOperationLog` and `ISubOperationLog` directly (unlike `RootOperationLog`/`ChildOperationLog`, which implement only one each) - a single disabled instance still needs to satisfy both, since `BeginSubOperation` hands itself back out as an `ISubOperationLog`. `EventId` and `AddProperty`/`Properties` behave normally, since callers may read them regardless of whether the operation logs anything; `IsEnabled` is hardcoded `false`; every other member is a no-op. The members the two interfaces share (all but `SetException`/`SetResult`) return different types per interface, so a single public method can't satisfy both - those are implemented explicitly, qualified by the closed generic interface that actually declares each one (`IOperationLogBase<IOperationLog>`/`IOperationLogBase<ISubOperationLog>`, not `IOperationLog`/`ISubOperationLog` themselves, since C# requires an explicit interface implementation to name the interface that *declares* the member, and these are all inherited from the generic base), each forwarding to a shared private `AddPropertyCore<T>` helper where there's real logic or just returning `this` where there isn't. Holds `eventId` and a lazily-allocated `List<KeyValuePair<string, object?>>?` properties field directly - since neither interface exposes a per-level `name`, a root and every sub-operation begun from it are behaviorally identical, so `BeginSubOperation` just returns `this` instead of allocating. Not a singleton (unlike the type it replaced) since it still carries per-operation state (`EventId`/`Properties`).
- `SynchronizedOperationLogBase<TInner>.cs` — internal abstract base (`where TInner : class, IOperationLogBase<TInner>`) holding the `IOperationLogBase<TInner>` members whose implementation doesn't depend on whether the wrapped log is a root or a sub-operation - every member `lock`s a shared `_gate` object before delegating to `_inner`, returning `TInner` via `(TInner)(object)this` (same reasoning as `OperationLog<TSelf>` above), and `BeginSubOperation` always wraps the resulting sub-operation in a `SynchronizedSubOperationLog` sharing the same `_gate`, regardless of whether `TInner` is `IOperationLog` or `ISubOperationLog`. Implements `IOperationLogBase<TInner>` itself (unlike `OperationLog<TSelf>`, which leans on `TSelf` instead) because every member here can already return `TInner` directly - there's no derived-type-specific return type to recover.  Deliberately does not implement `IJournalOwner` - see `OperationLogInterpolatedStringHandler.cs` above for why.
- `SynchronizedOperationLog.cs` / `SynchronizedSubOperationLog.cs` — opt-in (`threadSafe: true`) decorators over `SynchronizedOperationLogBase<TInner>`: `SynchronizedOperationLog : SynchronizedOperationLogBase<IOperationLog>, IOperationLog` wraps the root and adds `SetException`/`SetResult` (each `lock`s `_gate` then delegates to `_inner`), the two members `IOperationLog` adds beyond `IOperationLogBase<TSelf>`; `SynchronizedSubOperationLog : SynchronizedOperationLogBase<ISubOperationLog>, ISubOperationLog` wraps a sub-operation and adds nothing (the explicit `, ISubOperationLog` is required even though the base already implements `IOperationLogBase<ISubOperationLog>` - interface implementation is nominal, so a class has to name every interface it implements, even one whose members it already has). The whole operation tree — root plus every nested sub-operation, however deep — shares exactly *one* `_gate` object.
- `IJournalOwner.cs` — internal marker interface (`BeginJournalEntry(): StringBuilder`) implemented only by `OperationLog<TSelf>`, letting `OperationLogInterpolatedStringHandler` write directly into a real journal when one is safely available and fall back to a pooled private buffer otherwise.
- `ValueFormatting.cs` — `AppendValue<T>`/`AppendJson<T>`, both appending straight to the journal rather than returning a `string` (an `ISpanFormattable` value goes into the journal's current chunk directly; `AppendJson` transcodes pooled UTF-8 JSON bytes in via `ArrayPool<char>`). The point of both is that nothing is materialized as its own string on the way in — preserve that if you touch them.
- `ObjectPool.cs` / `OperationLogPools.cs` — a minimal `ConcurrentBag<T>`-backed pool backing `Journals` and `JsonWriters`; see the file's own comments for the sizing and counter rationale. `state.Properties` is deliberately *not* pooled — a plain `List<KeyValuePair<string, object?>>?` left `null` until the first `AddProperty`. `Journals` also backs `OperationLogInterpolatedStringHandler`'s private buffers, so on the `threadSafe: true` path it sees a rent/return per `Append` rather than one per operation.

Design notes worth remembering: the feature is **not thread-safe by default** — call sites that need concurrent access (e.g. sub-operations run via `Task.WhenAll`) must pass `threadSafe: true` to `BeginOperation` to get the `SynchronizedOperationLog`/`SynchronizedSubOperationLog` decorators. Root vs. sub-operation asymmetry is real, not just naming: only the root ever writes a log entry, whose message is the completed journal text, or gets an `Operation.Name`/`Operation.Result`/`Operation.StartTime`/`Operation.DurationSeconds` set of structured properties; sub-operations only ever contribute journal text. That asymmetry is now also enforced by the type system: `SetException`/`SetResult` exist only on `IOperationLog` (the root), not `ISubOperationLog` (what `BeginSubOperation` returns) - a sub-operation reference literally cannot overwrite the root's exception or result. A sub-operation that wants to record its own outcome uses `AppendException`/`AppendResult` instead, which both the root and every sub-operation have. `IOperationLog` and `ISubOperationLog` are deliberately unrelated interfaces (neither extends the other) - both extend the generic `IOperationLogBase<TSelf>` independently, closed over themselves, so every shared fluent member returns the exact interface it was called on rather than widening to a common type; this is also why `RSSL0006`'s implementation (`OperationLogChain.cs` et al., in `src/RandomSkunk.StructuredLogging.Analyzers/`) has to match a chained fluent call's containing type against the *open* `IOperationLogBase<>` definition via `OriginalDefinition`, not against `IOperationLog`/`ISubOperationLog` directly - Roslyn reports an inherited generic-interface member's containing type as the closed instantiation it was actually declared on.
